# Harness (Cursor) — 서브에이전트 팀과 스킬 설계

프로젝트에 맞는 하네스를 설계한다. 각 서브에이전트의 역할을 정의하고, 서브에이전트가 작업할 때 따를 스킬을 만든다.

## 핵심 원칙

1. 서브에이전트 정의는 `.cursor/agents/{name}.md`에, 스킬은 `.cursor/skills/{name}/SKILL.md`에 만든다. 서브에이전트에는 누가 일하는지를, 스킬에는 그 일을 어떻게 하는지를 적는다.
2. 작업 흐름에 따라 실행 방식을 고른다. 결과를 한 번 받으면 되면 단발 위임, 같은 전문가와 여러 번 주고받아야 하면 `resume`으로 이어 가는 위임, 독립 작업이 여럿이면 병렬 위임을 쓴다. 기준은 2단계에서 다룬다.
3. 서브에이전트의 `model`은 업무 성격으로 고른다. 기본값은 `inherit`이고, 절차가 단순하고 빠른 처리가 중요한 업무에만 더 가벼운 모델 ID를 지정한다.
4. 새 세션에서도 오케스트레이터 스킬을 찾을 수 있도록 `AGENTS.md`에 호출 조건과 변경 이력만 기록한다.
5. 실행 결과에서 배운 내용을 서브에이전트·스킬·`AGENTS.md`에 계속 반영한다(7단계).
6. 산출물은 사용자가 대화에 쓰는 언어로 작성한다. 사용자가 언어를 따로 정하면 그 언어를, 기존 하네스를 확장하면 기존 파일의 언어를 따른다.

## Cursor 기능 대응표

| 필요한 일 | Cursor에서 쓰는 것 |
| --- | --- |
| 전문가 역할 정의 | `.cursor/agents/{name}.md` (프론트매터 `name`, `description`, `model`, `readonly`, `is_background`) |
| 작업 방법 정의 | `.cursor/skills/{name}/SKILL.md` (프론트매터 `name`, `description`, 선택 `paths`, `disable-model-invocation`) |
| 서브에이전트 호출 | Task 도구. `subagent_type`에 서브에이전트 이름 지정 |
| 병렬 실행 | 메시지 한 번에 Task 호출 여러 개 |
| 맥락을 유지한 재대화 | Task 도구의 `resume`에 이전 agent ID 지정 |
| 진행 상황·의존 관계 관리 | 메인 에이전트의 `TodoWrite` |
| 서브에이전트 간 전달 | 메인 에이전트가 중계하거나 `_workspace/` 파일로 전달 |
| 세션마다 읽히는 프로젝트 지침 | `AGENTS.md` 또는 `.cursor/rules/*.mdc` |

서브에이전트끼리 직접 메시지를 주고받는 기능은 없다. 협업이 필요하면 메인 에이전트(오케스트레이터)가 결과를 받아 다음 서브에이전트의 프롬프트에 넣는다.

## 진행 절차

### 0단계: 현재 상태 점검

1. `.cursor/agents/`, `.cursor/skills/`, `AGENTS.md`를 읽는다. Cursor는 `.claude/agents/`, `.claude/skills/`도 읽으므로 함께 확인한다. 이름이 같으면 서브에이전트는 `.cursor/`가 우선한다.
2. 현재 상태에 따라 진행할 절차를 고른다.
   - **새로 구축**: 디렉터리가 없거나 비어 있으면 1단계부터 모두 실행한다.
   - **기존 구성 확장**: 아래 표에서 필요한 단계만 실행한다.
   - **운영·유지 보수**: 7단계로 이동한다.

   | 변경 내용 | 1단계 | 2단계 | 3단계 | 4단계 | 5단계 | 6단계 |
   | --- | --- | --- | --- | --- | --- | --- |
   | 서브에이전트 추가 | 0단계 결과 사용 | 실행 방식·위치만 결정 | 필수 | 전용 스킬이 필요할 때 | 오케스트레이터 수정 | 필수 |
   | 스킬 추가·수정 | 생략 | 생략 | 생략 | 필수 | 연결이 바뀔 때 | 필수 |
   | 구조·실행 방식 변경 | 생략 | 필수 | 영향받는 것만 | 영향받는 것만 | 필수 | 필수 |

3. 실제 서브에이전트·스킬 목록과 `AGENTS.md` 기록을 대조해 불일치를 찾는다.
4. 점검 결과와 실행 계획을 사용자에게 알리고 확인받는다.

### 1단계: 분야와 작업 분석

1. 사용자 요청에서 프로젝트의 분야와 목표를 파악한다.
2. 생성, 검증, 편집, 분석처럼 필요한 작업의 종류를 나눈다.
3. 실행 방식을 고를 수 있도록 작업 흐름을 확인한다.
   - 처리할 목록을 미리 나열할 수 있는가? 예: 파일 N개, 관점 M개
   - 산출물을 검증하고 다시 고치는 반복 절차가 필요한가?
   - 같은 전문가가 이전 맥락을 기억한 채 여러 번 작업해야 하는가?
4. 0단계에서 확인한 기존 서브에이전트·스킬과 겹치거나 충돌하는 부분을 찾는다.
5. 코드베이스를 살펴 기술 스택, 데이터 모델, 주요 모듈을 파악한다.
6. 사용자의 용어 수준에 맞춰 설명한다. 코딩 경험이 적은 사용자에게 전문 용어를 설명 없이 쓰지 않는다.

### 2단계: 실행 방식과 팀 구조 설계

#### 2-1. 실행 방식 선택

| 실행 방식 | 구현 | 알맞은 작업 |
| --- | --- | --- |
| **단발 위임** | Task 한 번 호출(포그라운드) | 결과만 한 번 받으면 되는 작업 |
| **병렬 위임** | 메시지 한 번에 Task 여러 개(필요하면 `run_in_background`) | 서로 독립인 작업 여러 개 |
| **이어 가는 위임** | 첫 호출의 agent ID를 `resume`에 넣어 재호출 | 같은 전문가가 피드백을 받아 고치거나 이전 맥락을 기억해야 하는 작업 |
| **스크립트 고정** | `scripts/`의 실행 코드 + 스킬의 단계 지시 | 처리 목록, 검증 기준, 반복 횟수를 코드로 정할 수 있는 작업 |

다음 순서로 결정한다.

1. 처리 목록·검증 기준·반복 조건을 코드로 표현할 수 있으면 스크립트로 고정하고, 판단이 필요한 부분만 서브에이전트에 맡긴다. 같은 방식으로 다시 실행할 수 있어야 하기 때문이다.
2. 같은 전문가와 여러 번 주고받아야 하면 이어 가는 위임을 쓴다.
3. 독립 작업이 여럿이면 병렬 위임, 아니면 단발 위임을 쓴다.
4. 단계마다 성격이 다르면 혼합하고, 오케스트레이터에 단계별 실행 방식을 적는다.

기본 실행은 서브에이전트 몇 개로 제한하고, 사용자가 "철저히", "전수"처럼 넓은 조사를 요구할 때만 늘린다.

#### 2-2. 팀 구성 방식 선택

- **파이프라인**: 앞 단계의 결과를 받아 순서대로 처리한다. 포그라운드 Task를 차례로 호출한다.
- **분산·통합**: 독립 작업을 병렬 위임한 뒤 메인이 결과를 합친다.
- **전문가 풀**: 입력에 맞는 서브에이전트만 골라 호출한다.
- **생성·검증**: 한 서브에이전트가 만들고 다른 서브에이전트가 검토한다. 생성자는 `resume`으로 이어 가며 수정한다.
- **감독자**: 메인 에이전트가 `TodoWrite`로 진행 상황을 보며 작업을 다시 배분한다.
- **계층형 위임**: 서브에이전트가 다시 서브에이전트를 부르는 구조는 한 단계로 제한한다.

정확성이 중요하면 다음 검증 방식을 조합한다.

- **적대적 검증**: 찾은 항목마다 검증 서브에이전트 N개를 붙이고, 과반이 `confirmed`로 판정한 항목만 통과시킨다.
- **심사위원단**: 시안 N개를 따로 만든 뒤 병렬로 심사하고 가장 좋은 시안으로 최종본을 만든다.
- **새 항목이 없을 때까지 반복**: 새로 찾은 항목이 K회 연속 0건이 될 때까지 탐색한다.
- **누락 검토자**: 마지막 서브에이전트에는 빠진 내용만 찾게 한다.

#### 2-3. 서브에이전트를 나누는 기준

필요한 전문 지식, 병렬 처리 가능 여부, 유지해야 할 맥락, 재사용 가능성으로 나눈다. 단일 목적의 짧은 작업(형식 변환, 체인지로그 생성 등)은 서브에이전트가 아니라 스킬로 만든다.

### 3단계: 서브에이전트 정의 작성

재사용할 전문가 역할은 `.cursor/agents/{name}.md`로 정의하고, Task 도구의 `subagent_type`에 그 이름을 지정해 부른다. 기본 제공 `explore`, `generalPurpose` 등으로 충분한 단발 작업에는 정의 파일을 만들지 않는다.

새 파일을 만들기 전에 기존 서브에이전트와 역할이 겹치는지 확인한다. 겹치면 새 이름으로 만들지 말고 기존 것을 쓰거나 확장한다.

#### 프론트매터

```markdown
---
name: api-spec-reviewer
description: API 명세의 형식과 누락을 검토한다. 명세 초안이 완성된 뒤 사용한다.
model: inherit
readonly: true
---
```

| 필드 | 작성 기준 |
| --- | --- |
| `name` | 소문자와 하이픈. 파일 이름과 맞춘다. |
| `description` | 메인 에이전트가 위임을 판단하는 근거. 하는 일과 호출 시점을 구체적으로 쓴다. |
| `model` | 기본 `inherit`. 단순·고속 업무에만 가벼운 모델 ID를 지정하고, 본문에 선택 이유를 한 줄 남긴다. 모든 서브에이전트에 고성능 모델을 일괄 지정하지 않는다. |
| `readonly` | 검토·분석만 하는 서브에이전트는 `true`. 산출물을 쓰거나 고치면 `false`. |
| `is_background` | 결과를 기다리지 않아도 되는 장기 작업만 `true`. |

#### 본문

핵심 역할, 작업 원칙, 입력·출력 규칙, 오류 처리, 최종 응답 형식을 적는다. 서브에이전트는 대화 기록을 보지 못하므로, 필요한 입력은 프롬프트나 파일로 받는다고 명시한다.

#### QA 서브에이전트를 둘 때

- 검증 스크립트를 실행해야 하므로 `readonly: false`로 둔다. `explore`는 읽기 전용이라 검증에 쓰지 않는다.
- 파일 존재 여부만 확인하지 않는다. 예를 들어 API 응답과 프런트엔드의 응답 구조를 대조한다.
- 전체 작업이 끝난 뒤 한 번만 검사하지 않고, 모듈을 완성할 때마다 검사한다.

### 4단계: 스킬 작성

각 서브에이전트가 따를 스킬을 `.cursor/skills/{name}/SKILL.md`에 만든다. 새로 만들기 전에 기존 스킬과 겹치는지 확인하고, 겹치면 기존 스킬을 연결하거나 확장한다.

#### 4-1. 디렉터리 구조

```
skill-name/
├── SKILL.md       # 필수. name(폴더 이름과 동일)과 description
├── scripts/       # 선택: 반복하거나 결과가 항상 같아야 하는 작업의 실행 코드
├── references/    # 선택: 필요할 때만 읽는 참조 문서
└── assets/        # 선택: 템플릿, 이미지 등
```

#### 4-2. description에 호출 조건 쓰기

Cursor 에이전트는 `description`을 보고 스킬을 불러올지 판단한다. 하는 일과 사용할 상황을 구체적으로 적고, 비슷하지만 쓰면 안 되는 경우도 구분한다. 사용자가 `/스킬이름`으로 부를 때만 쓰게 하려면 `disable-model-invocation: true`를 넣는다.

- **나쁜 예:** `"PDF 문서를 처리하는 스킬"`
- **좋은 예:** `"PDF 텍스트·표 추출, 병합, 분할, 회전, OCR 등 PDF 작업을 수행한다. 사용자가 .pdf 파일을 언급하거나 PDF 산출물을 요청하면 사용한다."`

#### 4-3. 본문 작성 원칙

| 원칙 | 적용 방법 |
| --- | --- |
| 이유부터 설명한다 | 규칙만 나열하지 말고 왜 필요한지 밝혀 예외 상황에서도 판단할 수 있게 한다. |
| 간결하게 쓴다 | `SKILL.md`는 500줄 미만. 세부 내용은 `references/`로 옮기고 언제 읽을지 적는다. |
| 원리로 일반화한다 | 특정 예시에만 맞는 규칙을 만들지 않는다. |
| 반복 코드는 미리 넣는다 | 여러 서브에이전트가 같은 코드를 다시 쓰면 `scripts/`에 넣는다. |
| 지시문으로 쓴다 | 한 가지 어미로 통일하고, 해야 할 행동이 드러나게 쓴다. |
| 경로는 `/`로 쓴다 | `scripts/helper.py`처럼 쓰고 `\` 구분자는 쓰지 않는다. |

### 5단계: 통합하고 실행 순서 정하기

오케스트레이터도 스킬이다. 서브에이전트와 스킬을 하나의 흐름으로 묶고, 누가 언제 어떤 순서로 일하는지 정한다. 기존 하네스를 확장할 때는 오케스트레이터를 새로 만들지 말고 기존 파일을 고친다.

#### 5-1. 오케스트레이터 구조

```
[오케스트레이터 스킬 — 메인 에이전트가 실행]
    ├── 0. 기존 _workspace/ 확인 (처음 실행 / 일부 재실행 / 새 입력)
    ├── 1. TodoWrite로 단계 등록
    ├── 2. Task(subagent_type: "a"), Task(subagent_type: "b")  ← 병렬이면 한 메시지에
    ├── 3. Task(subagent_type: "reviewer")  ← 앞 단계 파일 경로를 프롬프트에 포함
    ├── 4. REDO면 Task(resume: <a의 agent ID>, 수정 지시)
    └── 5. 결과 종합 후 사용자에게 보고
```

각 단계 위에 `**실행 방식:**`을 적는다. 서브에이전트 프롬프트에는 작업 디렉터리, 입력 파일, 출력 파일, 최종 응답 형식을 빠짐없이 넣는다.

#### 5-2. 데이터 전달

| 방법 | 사용할 때 |
| --- | --- |
| Task 반환 메시지 | 메인이 요약 결과를 직접 모을 때 |
| 다음 Task 프롬프트에 포함 | 앞 결과가 짧고 다음 서브에이전트가 바로 써야 할 때 |
| `_workspace/` 파일 | 데이터가 크거나 나중에 과정을 검증해야 할 때 |

- 중간 산출물은 `_workspace/`에 `{phase}_{agent}_{artifact}.{ext}` 형식으로 저장한다. 예: `01_analyst_requirements.md`
- 최종 산출물만 사용자가 지정한 경로에 저장한다. `_workspace/`는 사후 검증을 위해 남기고 `.gitignore`에 넣는다.

#### 5-3. 오류 처리

- 한 번 다시 시도하고 또 실패하면 해당 결과 없이 진행하되, 최종 보고에 누락 사실을 적는다. 충돌하는 데이터는 지우지 말고 출처와 함께 남긴다.
- 사용량 한도, 인증 만료, 권한 거부처럼 재시도해도 같은 실패는 재시도하지 않는다. 부분 산출물을 열어 어디까지 진행됐는지 확인하고 사용자에게 보고한다.
- 멈춘 서브에이전트의 빈 곳을 메울 때는 직접 확인한 사실만 반영한다. 서브에이전트의 판단을 추측해 채우지 않는다.
- 서브에이전트가 엉뚱한 결과를 내면 같은 유형을 새로 호출하고, 필요한 맥락을 프롬프트로 다시 넘긴다.

#### 5-4. 작업 규모

| 작업 규모 | 서브에이전트 호출 규모 |
| --- | --- |
| 소규모: 작업 10개 미만 | 2~5건 |
| 중규모: 작업 10~20개 | 약 10건 |
| 대규모: 작업 20개 초과 | 감독(메인) + 병렬 배치 여러 번 |

#### 5-5. `AGENTS.md`에 하네스 연결 정보 기록

````markdown
## 하네스: {도메인명}

**목표:** {핵심 목표 한 줄}

**호출 조건:** {도메인} 관련 작업을 요청받으면 `{orchestrator-skill-name}` 스킬을 사용한다. 단순 질문에는 직접 답해도 된다.

**변경 이력:**
| 날짜 | 변경 내용 | 대상 | 사유 |
| --- | --- | --- | --- |
| {YYYY-MM-DD} | 하네스 처음 구성 | 전체 | - |
````

서브에이전트·스킬 목록, 디렉터리 구조, 자세한 실행 규칙은 넣지 않는다. 이 정보는 `.cursor/agents/`, `.cursor/skills/`에서 관리한다.

#### 5-6. 후속 요청 처리

1. 오케스트레이터 `description`에 `다시 실행`, `재실행`, `업데이트`, `수정`, `보완`, `{부분 작업}만 다시`, `이전 결과를 바탕으로` 같은 표현을 넣는다.
2. 오케스트레이터 0단계에서 기존 작업 맥락을 확인한다.
   - `_workspace/`가 있고 일부만 고쳐 달라는 요청이면 해당 단계만 다시 실행한다.
   - `_workspace/`가 있고 새 입력이면 기존 디렉터리를 타임스탬프 이름으로 옮긴 뒤 새로 실행한다.
   - `_workspace/`가 없으면 처음부터 실행한다.
3. 서브에이전트 정의에 재호출 방법을 적는다. 이전 결과 파일이 있으면 읽고, 피드백이 있으면 해당 부분만 고친다.

### 6단계: 검증과 테스트

#### 6-1. 파일과 참조

- 모든 파일이 `.cursor/agents/`, `.cursor/skills/{name}/SKILL.md` 위치에 있는지 확인한다.
- 스킬 `name`이 폴더 이름과 같고 `description`이 있는지 확인한다.
- 오케스트레이터가 부르는 `subagent_type` 이름이 실제 서브에이전트 이름과 일치하는지 확인한다.
- Claude Code 전용 기능(`Workflow`, `SendMessage`, `TaskCreate`, `TeamCreate`, `tools:` 목록, `CLAUDE.md`)이 남지 않았는지 확인한다.

#### 6-2. 실행 방식별 검증

- **병렬 위임**: 병렬 호출을 메시지 한 번에 묶었는지, 결과를 빠짐없이 모으는지 확인한다.
- **이어 가는 위임**: agent ID를 저장해 `resume`에 넘기는지 확인한다.
- **파이프라인**: 각 서브에이전트의 입력이 앞 단계 출력과 맞는지 확인한다.
- **스크립트 고정**: 스크립트를 실제로 실행해 성공하는지 확인한다.

#### 6-3. 실행 테스트

1. 스킬마다 실제 사용자가 입력할 법한 요청 2~3개로 실행한다.
2. 가능하면 스킬 적용 실행과 기준 실행을 병렬로 수행해 개선 정도를 비교한다.
3. 문제가 나오면 특정 예시만 막는 규칙이 아니라 일반 원리로 고치고 다시 테스트한다.

#### 6-4. 호출 조건 검증

1. 스킬을 불러와야 하는 요청을 말투와 명시 수준을 달리해 10개 만든다.
2. 비슷하지만 다른 스킬이나 도구를 써야 하는 경계 사례 10개를 만든다. 명백히 무관한 요청은 경계를 검증하지 못한다.
3. 기존 스킬과 호출 조건이 겹치는지 확인한다.

#### 6-5. 테스트 시나리오 기록

오케스트레이터 스킬에 `## 테스트 시나리오`를 만들고 정상 흐름 한 가지와 오류 흐름 한 가지 이상을 적는다.

### 7단계: 운영·유지 보수와 개선

1. **현재 상태 점검**: `.cursor/agents/`, `.cursor/skills/`, 오케스트레이터 구성, `AGENTS.md`를 비교해 불일치 목록을 만들고 사용자에게 알린다.
2. **조금씩 추가·수정**: 한 번에 한 항목만 바꾸고 바로 검증한다.
3. **변경 이력 기록**: `AGENTS.md`에 날짜, 변경 내용, 대상, 사유를 적는다.
4. **변경 검증**: 파일 구조를 확인하고, 호출 조건에 영향을 주면 6-4를 다시 한다.

사용자가 회고나 피드백 반영을 요청하거나, 같은 피드백이 두 번 이상 나왔거나, 서브에이전트가 같은 원인으로 반복 실패하면 다음 순서로 개선한다.

1. 처음 구성과 현재 상태, 실패·피드백 기록을 비교해 원인을 찾는다.
2. 여러 상황에 적용할 수 있는 원리로 정리한다.
3. 해당 서브에이전트·스킬·오케스트레이터에 반영하고 `AGENTS.md` 변경 이력을 갱신한다.
